## Sistema de diseño (Sprint 4)

Establecido al notar inconsistencias acumuladas. **Toda pantalla nueva debe seguir esto. Página de referencia: `/panel/catalogos`.**

### Colores semánticos

- `emerald` → acción primaria, estado positivo (consulta firmada, paciente atendido)
- `blue` → información neutra, badges secundarios (asistente, permanente)
- `amber` → advertencia / borrador / validación inline
- `red` → destructivo / cancelado / no asistió / errores
- `gray` → neutro, fondos, texto secundario

### Spacing y radius

- **Cards principales**: `bg-white rounded-2xl border border-gray-200 p-5`
- **Sub-items dentro de cards** (filas de lista, items en form): `bg-gray-50 rounded-lg p-3`
- **Inputs y selects**: `border border-gray-200 rounded-lg px-3 py-2 text-sm`
- **Pills/badges**: `rounded-full px-2.5 py-0.5 text-xs font-medium`
- **Modales**: `rounded-2xl shadow-xl p-6`
- Gap consistente: `gap-3` para grupos relacionados, `gap-5` entre secciones

### Botones — usar `<Button>` de `src/components/ui/Button.tsx`

4 variants:
- `primary` → solid emerald: `bg-emerald-600 hover:bg-emerald-700 text-white`
- `secondary` → solid gray: `bg-gray-100 hover:bg-gray-200 text-gray-700`
- `subtle` → soft pill: `bg-emerald-50 hover:bg-emerald-100 text-emerald-700 border border-emerald-200`
- `danger` → solid red: `bg-red-600 hover:bg-red-700 text-white`

3 sizes: `sm` (`px-3 py-1.5 text-xs`), `md` (`px-4 py-2 text-sm`, default), `lg` (`px-5 py-2.5 text-sm font-semibold`).

### Patrones de guardado

| Tipo de flujo | Patrón | Ejemplo |
|---|---|---|
| Transaccional / firma | Botón explícito `Guardar` o `Firmar`, sticky bottom | Firmar consulta, registrar paciente walk-in |
| Edición incremental dentro de un draft | Autosave on blur, sin botón | Notas de un diagnóstico, dosis de un medicamento |
| Switches / acciones reversibles | Mutación inmediata al click, optimistic UI cuando aplica | Toggle publicar perfil, marcar permanente |

### Patrones de acceso a entidades

- Si la entidad tiene página propia (`/panel/pacientes/:id`) → row clickeable, sin botón explícito
- Si la entidad NO tiene página propia → botón explícito en la fila
- Detail panel lateral (slide-in desde derecha) cuando navegar perdería contexto (ej: detalle de cita en calendario)
- Modal cuando es una acción puntual sin estado persistente (ej: confirmar firma, editar paciente)

### Catálogos por médico

- Patrón establecido: `diagnoses`, `medications` (cada uno con `doctor_id`, `is_active`, `usage_count`)
- Búsqueda + create-inline desde el flujo de uso (consulta) usando `<Combobox>`
- Página de admin formal en `/panel/catalogos` con tabs (una por catálogo)
- Soft-delete vía `is_active=false` — nunca hard-delete porque hay FK desde consultas firmadas (inmutables)
- Sort por `usage_count desc` para mostrar primero los más usados

### Regla CRUD: hard-delete vs soft-delete (clínica/legal)

**Default: si la entidad puede tener historia clínica o referencias inmutables → soft-delete.**

Razón: en sistemas clínicos hay obligación de trazabilidad. Borrar un paciente, una cita, un diagnóstico de catálogo o un medicamento prescrito previamente rompe el historial clínico-legal. La auditoría debe poder reconstruir qué se hizo, cuándo y por quién — siempre.

| Entidad | Patrón | Razón |
|---|---|---|
| `patients` | soft (`is_active`) | Tiene consultas firmadas, recetas, citas históricas |
| `diagnoses` (catálogo) | soft (`is_active`) | FK desde consultation_diagnoses inmutables |
| `medications` (catálogo) | soft (`is_active`) | FK desde prescriptions inmutables |
| `appointments` | soft (estado `cancelada` o `no_asistio`) | Tienen vitals, posibles consultas |
| `consultations` con contenido | sin delete | Si tiene texto/diagnósticos/recetas/vitales, no hay descarte — el médico la firma o la deja draft |
| `consultations` SIN contenido | hard-delete OK | Caso "abrí por error y nunca tipeé nada" — acepta delete cascade |
| `consultation_diagnoses`, `prescriptions` (mientras la consulta sea draft) | hard-delete OK | Edición incremental dentro del borrador |
| `availability_overrides` | hard-delete OK | No tiene historia clínica |
| `clinic_members` (asistentes) | soft (`is_active=false`) | Mantiene auditoría de quién accedió cuándo |
| Items de receta o draft (`prescriptions`, `consultation_diagnoses`) en consulta firmada | sin delete | La consulta ya es inmutable |

**Implementación de soft-delete en UI:**
- Toggle visible "Activo/Inactivo" en lugar de botón eliminar
- Lista por default solo activos; checkbox "Mostrar inactivos" para verlos
- Inactivos no aparecen en autocomplete/buscadores de los flujos de uso

**Audit log siempre captura el snapshot del OLD_DATA en el trigger** — incluso para hard-deletes legítimos, el `audit_log` preserva el JSON completo de lo borrado.

## Patrones de infraestructura introducidos en Sprint 3

### useClinicContext (`src/hooks/useClinicContext.ts`)
Hook unificado que devuelve `{ profileId, role, clinicId, doctorId, doctorName }` para doctor o asistente. Toda página del panel debe usarlo en lugar de hacer lookup inline a `from('doctors')`. Ya está integrado en CitasPage, PacientesPage, BloqueosPage, PerfilPage. Próximas páginas deben seguir el mismo patrón.

### useClinicContext con asistentes
- Si `role='assistant'`: busca en `clinic_members` y luego el doctor primario de esa clínica (el primero por `created_at`)
- Multi-doctor por clínica NO está soportado — siempre toma el primer doctor (Sprint 4: agregar selector)

### Audit log
- `src/services/auditLog.service.ts` con `logAuditEntry()`
- Se llama desde frontend tras updates relevantes (no bloquea si falla)
- Schema: `audit_log` tiene action ENUM ('select','insert','update','delete')

### Notificaciones del panel (S3-01)
- NO usa la tabla `notifications` (que es para SMS/email salientes a pacientes vía Twilio)
- Se derivan de `appointments` en `src/services/panelNotifications.service.ts`:
  - `new_booking`: cita creada con `source='lucy_directorio'` en últimas 24h
  - `cancellation`: cita con `cancelled_at` en últimas 24h
- Read/unread con un solo timestamp en `localStorage` (`lucycare_panel_notif_seen_at`)

## Schema crítico verificado

- `appointment_statuses`: id, name, display_name, color, is_final, funnel_order
- `audit_log`: id, user_id, action (ENUM), table_name, record_id, old_data jsonb, new_data jsonb, ip_address, created_at
- `appointments` tiene campos: cancellation_reason, cancelled_at, cancelled_by, source ('manual'|'lucy_directorio'|'lucy_seguimiento')
- `patients` tiene campos completos: full_name, phone, email, document_type+document_number, date_of_birth, gender, patient_type, blood_type, allergies, notes, emergency_contact_*, photo_url, is_active, profile_id (nullable)
- `doctors`: bio, consultation_fee, experience_years, languages[], license_number, specialty_id, is_published, is_verified, booking_enabled, lucy_status, education jsonb
- `profiles`: full_name, email, phone, avatar_url, role ('patient'|'doctor'|'assistant'|'admin')
- `clinic_members`: clinic_id, profile_id, role ('owner'|'doctor'|'assistant'), is_active
- `notifications` (NO usada por el panel): para SMS/email salientes — recipient_id, channel, type, status, scheduled_at

## Estados de cita y transiciones

- programada → confirmada → en_sala → atendida (final)
- cancelada (final), no_asistio (final)
- Validaciones extremas implementadas: no marcar 'atendida' con >24h de anticipación; no marcar 'no_asistio' antes de la hora de la cita

## Cómo crear una asistente (manual hasta tener S5-06)

```sql
-- 1. La asistente se registra como paciente normal vía OTP
-- 2. Doctor o admin ejecuta:
UPDATE profiles SET role='assistant' WHERE phone='+503...';
INSERT INTO clinic_members (clinic_id, profile_id, role, is_active)
VALUES ('<clinic-uuid>', '<profile-uuid>', 'assistant', true);
```
