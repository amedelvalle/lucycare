10 · MÉTODO — cómo trabajar en este proyecto
================================================================================

  ── REGLAS OPERATIVAS ──
  · UN FRENTE FUNCIONAL A LA VEZ. El owner DECIDE; el dev EJECUTA.
  · NO merge sin autorización. NO abrir PR sin autorización.
  · EL OWNER aplica el SQL en el SQL Editor; el dev prepara la migración y corre
    los check/smoke.
  · PR que toca DB → migración + `check-s7_NN.mjs` (+ smoke si aplica).
  · Para cambios de UI: pedir preview / OK visual del owner antes de mergear.
  · NO mezclar SEO / Analytics / Auth / Clínico / DB en un mismo PR.
  · Cambios PEQUEÑOS Y REVERSIBLES. Copy en TUTEO.
  · Cierre estándar tras cada merge: HEAD, PRs, migraciones,
    `main == origin/main`, `git status` vacío, rama borrada local+remoto,
    0 PRs abiertos, sin residuos.

  ── CÓMO PEDIR Y CÓMO EJECUTAR (aprendido en el ciclo #353) ──
  · UNA INSTRUCCIÓN CONSOLIDADA POR ETAPA funciona mejor que muchas parciales:
    reduce ida y vuelta y evita que el árbol cambie mientras alguien aplica.
  · SEPARAR bloqueantes reales de hardening opcional. No todo hallazgo merece
    convertirse en trabajo.
  · ANTE UN FALLO: medir el ESTADO REAL → UNA corrección → UNA validación. No
    encadenar hipótesis.
  · EVITAR LA PROLIFERACIÓN de checks y hardenings cuando el frente ya es
    funcional. Cada guarda nueva es código que puede fallar por su cuenta.

  ── VALIDAR EL INSTRUMENTO, NO SOLO EL FIX ──
  Corre la MISMA medición contra el código ANTERIOR para comprobar que el
  defecto se reproduce (A/B). Un test que solo pasa "después" no prueba nada.
  Y usa MUTATION TESTS: introduce la regresión y comprueba que el check la caza.
  Si no la caza, la aserción es DECORATIVA.

  Incluye también EXPECTATIVA INVERTIDA: mutaciones legítimas que el check NO
  debe cazar. Sin ellas no se detectan los FALSOS POSITIVOS — y un falso
  positivo puede impedir aplicar una migración correcta.

  ── DOS LECCIONES QUE COSTARON CARO ──

  1) `pg_proc.prosrc` INCLUYE LOS COMENTARIOS.
     El primer apply de `s7_82` abortó con «POST falló: el WARNING usa SQLERRM»:
     la guarda se disparó con SU PROPIO COMENTARIO. `check-s7_82.mjs` sí quitaba
     comentarios y daba PASS.
     REGLA: UNA GUARDA SQL Y SU EQUIVALENTE EN JS DEBEN MEDIR EXACTAMENTE LA
     MISMA REPRESENTACIÓN. Si una normaliza y la otra no, la discrepancia es
     invisible en local y solo aparece al aplicar en producción.
     Y las comprobaciones de PRESENCIA tienen el fallo simétrico: pasarían si el
     código pierde la llamada pero un comentario la nombra.

  2) `String.prototype.replace(x, cadena)` INTERPRETA `$$` EN EL REEMPLAZO.
     Convirtió `AS $$` en `AS $` y `$$;` en `$;` al empalmar SQL por programa.
     Silencioso: el archivo se escribió sin error. Usa splice de array o
     split/join, NUNCA `replace` con cadena, para inyectar SQL.

  ── OTRAS TRAMPAS YA PISADAS ──
  · Comprobar una prohibición contra el ARCHIVO ENTERO cuando las guardas POST
    nombran a propósito lo prohibido → acota al CUERPO de la función.
  · Medir ORDEN cuando lo que importa es ANIDAMIENTO: quitar un `BEGIN` deja el
    `EXCEPTION` en la misma posición relativa y un check por índices lo deja
    pasar. Cuenta la estructura.
  · `includes('id')` matchea "Especialidad".
  · Quitar comentarios `//` de TypeScript con un regex global se come la mitad
    de `'https://lucycare.app'`.
  · `Blob.text()` ELIMINA el BOM por especificación: para verificarlo hay que
    mirar los BYTES.
  · Un `head:true` con `count` sobre una tabla INEXISTENTE devuelve 204 sin
    error: parece que existe. Sonda fiable = `select` normal.
  · PGRST202 significa "no hay sobrecarga que case", no necesariamente "la
    función no existe": un nombre de parámetro equivocado da lo mismo.
  · 42501 sobre una RPC PRUEBA que existe (una inexistente daría PGRST202) y de
    paso confirma sus grants.
  · PostgREST NO expone `pg_catalog` ni las funciones que devuelven `trigger`.
    Todo lo de catálogo se verifica en el SQL Editor.
  · Tras aplicar DDL, el SCHEMA CACHE de PostgREST puede quedar obsoleto y
    devolver PGRST205/PGRST202 aunque el objeto exista. NO concluyas "la
    migración falló": verifica con `to_regclass`/`to_regprocedure` primero.
  · SIEMPRE incluye un CONTROL DE SANIDAD que DEBA pasar. Si también falla, el
    defecto es tuyo.

  ── SHELL (Windows) ──
  Evita heredocs grandes y `node -e` con escapes anidados: en este proyecto han
  corrompido regex y template literals VARIAS VECES, en silencio (`\s` → `s`,
  `$$` → `$`). Escribe los scripts con el editor de archivos y verifica después
  que las aserciones nuevas están realmente ahí.
  En PowerShell 5.1, `curl` es alias de `Invoke-WebRequest`: usa `curl.exe`.
  `npx supabase <lo que sea>` deja `supabase/.temp/cli-latest`, que NO está en
  `.gitignore`. Bórralo antes de stagear.

  ── SMOKES SQL ──
  No uses tablas temporales en el SQL Editor (42P01 / 3F000). Patrón vigente:
  variable `jsonb` + `set_config`/`current_setting` dentro de BEGIN … ROLLBACK.
  El SQL Editor NO MUESTRA LOS NOTICE: haz que el bloque termine con
  `IF v_fail > 0 THEN RAISE EXCEPTION`, así "completar sin excepción" ES la
  prueba de 0 FAIL.
  Un smoke que inserta en tablas con trigger de auditoría DEBE ir en
  BEGIN…ROLLBACK: `audit_log` es inmutable desde s7_71b y lo que entre ahí no se
  corrige.
